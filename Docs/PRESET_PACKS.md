# Preset Packs

Status (2026-10-18): subsystem, tests, local server and backend staged. **Not yet
wired into CMake, the processor or the editor**, and the backend is **not
deployed** (see [Integration status](#integration-status)).

ChordEngine presets can be distributed as *Preset Packs*. The 12 built-in
presets form the **Stock Pack** (`chordengine-stock`), which is compiled into the
plug-in and always available to anyone with product access. Further packs are
listed on a store page and can be downloaded by active **Music-Prod+** members;
a member can download every released pack.

| Path | What |
| --- | --- |
| `Source/Packs/PackFormat.{h,cpp}` | format, validator, deterministic writer, `makeStockPack()` |
| `Source/Packs/PackLibrary.{h,cpp}` | installed packs on disk, atomic install, scan |
| `Source/Packs/PackStoreClient.{h,cpp}` | catalog + download client, transport seam, store-view status merge |
| `Resources/Packs/chordengine-stock.json` | the stock pack as a file (generated, byte-checked by the tests) |
| `Resources/Packs/chordengine-test-pack.json` | "ChordEngine Test Pack", 4 presets, downloadable |
| `Tests/PackTests.cpp` | standalone test (format, library, client, status table) + `--e2e` mode |
| `Tools/LocalPackServer.py` | stdlib-only local emulation of the store function |
| `Backend/` | edge function + migration to port into the music-prod.com Supabase repo |

## Pack format (`chordengine-pack`, formatVersion 1)

One UTF-8 JSON document, at most **256 KiB**:

```json
{
  "format": "chordengine-pack",
  "formatVersion": 1,
  "slug": "chordengine-test-pack",
  "name": "ChordEngine Test Pack",
  "version": "1.0.0",
  "author": "Music-Prod",
  "description": "Four test presets ...",
  "presets": [
    { "name": "Test Gospel", "voicing": "close", "triggerMap": [7, 17, 8, "... 73 ints"] }
  ]
}
```

A preset is exactly what a built-in preset is (`Core/ChordPresetSystem`): a
voicing style and a trigger map with one code per MIDI note 24..96 (73 codes).
Each code is `templateIndex * 7 + scaleDegree`: `code % 7` is the scale degree
(0 = I ... 6 = vii) and `code / 7` the chord template, 0..9 =
TRI, TRI7, TRI79, SUS4, SUS47, SUS2C, STACK9, STACK11, STACK13, OPEN5. So codes
run 0..69.

### Validation rules (`packs::parse`)

| Field | Rule |
| --- | --- |
| whole document | ≤ 262 144 bytes, valid UTF-8, a JSON object |
| `format` | exactly `"chordengine-pack"` |
| `formatVersion` | the integer `1` (a string `"1"` or `2` is refused) |
| `slug` | `^[a-z0-9][a-z0-9-]{1,62}$` |
| `name` | 1..64 printable characters, no surrounding whitespace |
| `version` | `MAJOR.MINOR.PATCH`, decimal integers (no pre-release suffix) |
| `author` | optional (default `"Music-Prod"`), 1..64 printable characters |
| `description` | optional, ≤ 512 characters |
| `presets` | array of 1..64 presets |
| `presets[].name` | 1..40 printable characters (no control characters, no surrounding whitespace); unique within the pack ignoring case |
| `presets[].voicing` | `"close"`, `"spread"` or `"open"` |
| `presets[].triggerMap` | exactly 73 JSON integers, each 0..69 (no floats, strings or booleans) |
| anything else | unknown keys are ignored at every level |

`isStock` is never read from JSON; it is true only for the slug
`chordengine-stock`, and the library refuses to install that slug from disk or
the network.

`packs::toJson` writes a canonical form (fixed key order, one trigger map per
line, trailing newline), so writing a pack twice gives identical bytes and a
reproducible SHA-256. Both files in `Resources/Packs` are in canonical form (the
tests check it).

### The stock pack

`packs::makeStockPack()` builds the stock pack from `ChordPresetSystem` itself,
so it is by construction the built-in maps; the plug-in never needs the JSON
file. `Resources/Packs/chordengine-stock.json` exists for the store (and the
backend seed) and is generated by

```sh
ChordEnginePackTests --emit-stock Resources/Packs/chordengine-stock.json
```

The default test run fails if the file ever differs from `toJson(makeStockPack())`.

### The test pack

`chordengine-test-pack` 1.0.0, four presets built from the same code system,
each laid out per octave (white keys = diatonic degrees I..vii, black keys =
colour chords), with a different template per register:

| Preset | Voicing | White keys (low / mid / high register) | Black keys |
| --- | --- | --- | --- |
| Test Gospel | close | TRI7 / STACK9 / STACK11 | IV9, V7sus4, ii11, vi9, V13 |
| Test Jazz Ninths | close | TRI7 / TRI79 / TRI79 | ii13, V13, IV11, vi9, vii9 |
| Test Sus Pads | open | SUS2C / SUS4 / SUS47 | OPEN5 on I, IV, V, vi, ii |
| Test Power | spread | OPEN5 everywhere | plain triads on I, IV, V, vi, vii |

Registers: notes 24..47, 48..71, 72..96. The tests check that all four maps
differ from each other and from every stock map, and that every code names a
real template and resolves to a chord for every note in every scale.

## Storage

Downloaded packs: `<storage root>/Packs/<slug>.chordpack`, where the storage
root is the licensing one, `~/Library/Application Support/Music-Prod/ChordEngine/`
on macOS (`PackLibrary::defaultPacksDirectory()`). The file is the exact bytes
the store served.

- **install** verifies the SHA-256 from the store's answer *before* parsing,
  validates the pack, requires its slug to be the one requested, writes
  `.install-<slug>.tmp` in the same folder and renames it over the old file
  (`juce::File::replaceFileIn`: POSIX `rename`, Windows `ReplaceFile`). A failed
  install changes nothing.
- **scan** loads every `*.chordpack`, skipping (and reporting) files that fail
  validation, whose slug differs from the file name, or that claim the stock
  slug; it deletes orphaned `.install-*.tmp` files.
- **list** is the stock pack first, then installed packs by name.

### Who may use what

- Stock presets: anyone with product access; never gated by packs code.
- Downloaded packs: usable only while the cached, verified entitlement says the
  account is an active Music-Prod+ member (`PackLibrary::usablePacks(member)`;
  pass `isSignedIn(snapshot) && snapshot.cached.subscribed`). This client-side
  gate is a convenience: the real gate is the server refusing downloads to
  non-members.

## Store contract

Function `chordengine-packs` at the licensing origin
(`licensing::authOrigin`, overridable in `PackStoreClient`'s constructor).
No API key and no Supabase JWT (`verify_jwt = false`); identity is the plug-in
token that `vyre-plugin-auth` already issues for product `chordengine`.

**Catalog** (public): `GET <origin>functions/v1/chordengine-packs?action=catalog`

```json
{ "version": 1, "generated_at": "2026-10-18T12:00:00Z",
  "packs": [ { "slug": "chordengine-stock", "name": "ChordEngine Stock Pack",
               "description": "...", "version": "1.0.0", "preset_count": 12,
               "is_stock": true, "size_bytes": 4522, "sha256": "cb30...",
               "artwork_url": "https://... (optional)", "sort_order": 10 } ] }
```

The client refuses a document with another `version` and skips (but reports)
individual malformed entries. An artwork URL that is not https is dropped.

**Download**: `POST <origin>functions/v1/chordengine-packs`
`{"action":"download","token":"<plugin token>","slug":"<slug>"}`

| Status | Body | Client outcome |
| --- | --- | --- |
| 200 | `{"ok":true,"slug","version","sha256","download_url"}` (signed URL, 10 min) | fetch + install |
| 401 | `{"error":"unauthorized"}` (unknown/revoked token, or not a ChordEngine token) | `unauthorized` |
| 403 | `{"error":"membership_required","unlock_url":"https://music-prod.com/plus","unlock_message":"..."}` | `membershipRequired` |
| 404 | `{"error":"not_found"}` | `notFound` |

Then the client GETs `download_url`:

- only `https://` (plain `http://` is allowed only to `127.0.0.1` / `localhost`
  for the local server); user-info hosts and other schemes are refused before
  any request; redirects are not followed;
- the body is read with a hard 256 KiB bound (`tooLarge` beyond it);
- the bytes must hash to the `sha256` of the 200 answer, then
  `PackLibrary::install` runs.

Callbacks arrive on the message thread and never after the client is
destroyed. The production transport (`HttpPackStoreTransport`) runs `juce::URL`
on a private one-worker `ThreadPool`, like `MusicProdAuthService`.

## Store view

`packs::mergeListings(catalog /*nullable*/, library, {signedIn, subscribed})`
returns one row per pack: stock first, then catalog order, then installed packs
the catalog does not list (offline, or withdrawn). "Member" means
`signedIn && subscribed`.

| Situation | Status | Text |
| --- | --- | --- |
| stock pack (always) | `builtIn` | `Built in · 12 presets` |
| member, installed, current | `installed` | `Installed · 4 presets` |
| member, installed, catalog newer | `updateAvailable` | `Update available · 1.2.0` |
| member, not installed | `available` | `Click to download` |
| signed in, not a member (installed or not) | `requiresMembership` | `Music-Prod+ required` |
| signed out (installed or not) | `signInRequired` | `Sign in to download` |

Each row also says `usable` (presets may be offered) and `canDownload`
(a click should call `download()`).

## Local server and tests

```sh
# Store emulation on 127.0.0.1 (prints "LISTENING <port>"):
python3 Tools/LocalPackServer.py --port 8765
#   tokens: member-token -> 200, nonmember-token -> 403, anything else -> 401
#   --tamper serves altered bytes (the client must refuse the checksum)
#   --port 0 picks a free port

# Unit/contract tests (no network):
ChordEnginePackTests

# End-to-end against the local server with the real HTTP transport:
ChordEnginePackTests --e2e http://127.0.0.1:8765/
```

`--e2e` only accepts a `127.0.0.1` / `localhost` origin, so it can never be
pointed at production.

## Integration status

**Wired into the plug-in (2026-10-18):**

- CMake: library `ChordEnginePacks` (linked into every plug-in target and every
  test that compiles the processor) and the `ChordEnginePackTests` CTest.
- Core: `ChordPresetSystem::resolve(const std::uint8_t* triggerMap, ...)` and
  `CustomChordPreset`; `ChordEngineCore::setCustomPreset` makes a pack preset
  replace the stock preset for generation. The 12 stock maps are untouched.
- Processor: `setPackPreset` / `clearPackPreset` / `packPreset`. Hand-off to the
  audio thread is lock-free (the audio thread only try-locks). The host state
  stores the pack preset **with its chord map** (`packSlug`, `packName`,
  `packPreset`, `packVoicing`, `packMap` attributes), so a project plays the
  same chords after reload or on another machine, even without the pack
  installed.
- Editor: a third page, **PACKS**. It fetches the catalog the first time it
  opens, lists Built in / Installed / Download / Music-Prod+ required / Sign in,
  and downloads with the account token. Presets of usable installed packs are
  listed under the pack's name in the CHORD PRESET menu and stepped through by
  the arrows. "Usable" means signed in with a cached active Music-Prod+
  membership (`isSignedIn && cached.subscribed`).
- Tests: integration case 21 (pack preset generation, refusal of a bad map,
  state round trip, clearing) and functional case 23 (PACKS page, catalog fetch
  only on open, no download without membership, restored preset shown).

**Developer check against the local server:** start
`python3 Tools/LocalPackServer.py --port 8765` and launch the host with
`CHORDENGINE_PACK_STORE_ORIGIN=http://127.0.0.1:8765/`. Only loopback origins
are honoured. Downloads use the account token, so the local server's
`member-token` path is exercised by `ChordEnginePackTests --e2e`, not from the
editor.

**Not done (needs the owner):**

  files to the private `chordengine-packs` bucket, and deploy. Until then the
  production catalog request fails, and the PACKS page says "Store unavailable -
  showing installed packs".
- Decide whether the test pack should be seeded `released` (public) or `draft`
  (admins only). The migration currently seeds it `released`.
